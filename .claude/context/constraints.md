# CONSTRAINTS

이 프로젝트 작업 시 아래 제약을 반드시 지킨다.

---

## 코드 수정 제약

1. 요청 범위를 벗어난 리팩토링 금지
2. 함수명/모듈명/책임이 이미 명확하면 함부로 변경 금지
3. 로그 메시지는 운영 추적이 가능하도록 유지
4. 예외 처리는 “숨기기”보다 “원인 노출” 우선
5. 기존 저장 구조를 깨는 변경은 사전 영향 분석 없이 진행 금지

---

## 문서 작성 제약

1. 코드로 확인되지 않은 내용 작성 금지
2. “추정”, “아마”, “대충” 같은 표현 금지
3. 실제 파일/모듈/흐름 중심으로 작성
4. 사람이 유지보수에 바로 쓸 수 있게 작성

---

## 토큰 사용 제약

1. 관련 없는 파일까지 넓게 읽지 말 것
2. 한 번에 한 작업만 해결
3. 필요 시 먼저 확인할 파일 목록부터 좁힐 것
4. 긴 설명보다 구조화된 요약 우선

---

## 운영/배포 제약

1. 운영 명령어는 실제 실행 전 영향 설명
2. 삭제/초기화/재구축 계열 명령은 신중하게 제안
3. 로그 확인 경로와 복구 순서를 함께 제시
4. cron, docker, systemd, git 권한 문제를 항상 분리해서 본다

---

## 품질 제약

1. 중복 뉴스가 브리핑에 반복되면 품질 저하로 간주
2. 중요하지 않은 기사 노출이 많으면 선정 로직 문제로 본다
3. 특정 카테고리 편향이 심하면 필터/분류/정렬 문제로 본다
4. 브리핑은 “정보량”보다 “가독성 + 중요도 우선”이다
