# DATA RETENTION

## 목적

뉴스 및 운영 데이터를 일정 기간 이후 정리하여  
DB 크기 증가를 억제하고, 조회 성능과 운영 안정성을 유지한다.

이 문서는 "무엇을 얼마나 보관할 것인가"에 대한 정책 기준을 정의한다.

---

## 적용 범위

현재 시스템에서 관리하는 주요 데이터는 아래와 같다.

### 1. news_articles
- 뉴스 원문 데이터
- RSS 기반 수집 결과
- dedup 기준 데이터 (url UNIQUE, title_hash)

### 2. article_symbols
- 기사와 종목 간 매핑 데이터
- news_articles 기반 파생 데이터
- `ON DELETE CASCADE` 적용됨

### 3. job_metrics
- job 실행 로그 및 상태 기록
- collect / briefing / cleanup 결과 포함

---

## 데이터 특성

| 테이블 | 성격 | 재생성 가능 여부 | 비고 |
|--------|------|------------------|------|
| news_articles | 원문 데이터 | 불가 | 시간이 지나면 원문 소스 사라질 수 있음 |
| article_symbols | 파생 데이터 | 가능 | news_articles 기반 재생성 가능 |
| job_metrics | 운영 로그 | 불필요 | 최신 상태만 의미 있음 |

---

## 보존 정책

### news_articles
- 보존 기간: **90일**
- 이유:
  - 브리핑은 최신 24시간 기준
  - 90일이면 추세 확인 및 비교 충분
- 처리 방식:
  - 기간 초과 데이터는 **DELETE**

---

### article_symbols
- 별도 보존 기간 없음
- news_articles 삭제 시 **CASCADE로 자동 삭제**
- 별도 cleanup 대상 아님

---

### job_metrics
- 보존 기간: **30일**
- 이유:
  - 장애 추적 최소 7일 필요
  - 30일이면 월간 추세 확인 가능
- 처리 방식:
  - 기간 초과 데이터는 **DELETE**

---

## archive 정책

현재 시스템에서는 archive를 사용하지 않는다.

### 이유
- 오래된 뉴스 데이터를 다시 조회하는 요구가 없음
- 규정/감사 목적 보존 필요 없음
- 운영 복잡도 증가 대비 효과 낮음

결론:
👉 **모든 대상은 archive 없이 delete로 처리한다**

---

## cleanup 방식

- 수동 삭제 금지
- job 기반 자동 실행

구현 위치:
- `app/jobs/cleanup_job.py`

실행 방식:
- cron 또는 docker compose job 실행

---

## 설계 원칙

1. 단순한 구조 유지 (delete 중심)
2. 최소한의 정책으로 운영
3. 과도한 보존보다 안정적인 정리 우선
4. 필요 시 보존 기간은 늘릴 수 있지만 줄이는 것은 신중하게

---

## 검토 기준

cleanup 정책을 변경할 때는 아래 기준으로 판단한다.

1. 해당 데이터가 현재 브리핑 품질에 기여하는가
2. 삭제 시 기능/분석에 문제가 발생하는가
3. 재생성 가능한 데이터인가
4. 저장 비용 및 성능에 영향을 주는가
