# ARCHITECTURE

이 프로젝트는 뉴스 수집부터 브리핑 생성까지 이어지는 파이프라인형 구조를 가진다.

---

## 목표 흐름

뉴스 소스 수집
→ 원문 정규화
→ 중복/품질 필터링
→ 분류
→ 저장
→ 브리핑 생성
→ 출력/전송
→ 스케줄링 및 운영 모니터링

---

## 주요 구성 요소

### 1. Collector
역할:
- RSS 및 외부 뉴스 소스 수집
- 기사 메타데이터 파싱
- 수집 시간 기록

핵심 관심사:
- 수집 실패 처리
- 중복 URL 처리
- source별 포맷 차이 대응
- published_at / collected_at 일관성

---

### 2. Classifier
역할:
- 뉴스 카테고리 분류
- article_type 분류
- 필요 시 중요도/브리핑 적합성 판단

핵심 관심사:
- 분류 기준 일관성
- 잘못된 라벨 최소화
- 브리핑 품질과 직접 연결되는 분류 정확도

---

### 3. Storage / Repository
역할:
- 수집 결과 저장
- 중복 제거 조회
- 브리핑 생성 대상 조회
- 메트릭 저장

핵심 관심사:
- 중복 insert 방지
- 브리핑 생성 시 필요한 조회 성능
- 데이터 보존 정책 적용 가능성

---

### 4. Briefing Builder
역할:
- 저장된 기사 중 브리핑 대상 선정
- 중복/유사 내용 정리
- 섹션별 요약 생성
- 아침 브리핑 포맷 구성

핵심 관심사:
- 같은 내용 반복 제거
- 노이즈 기사 배제
- 카테고리 균형
- 중요한 뉴스 우선 정렬

---

### 5. Renderer / Output
역할:
- 브리핑 결과를 사람이 읽기 쉬운 텍스트/메시지로 변환
- Slack, Telegram, 콘솔, 파일 등 출력 경로 대응 가능

핵심 관심사:
- 가독성
- 섹션별 일관된 형식
- 길이 제한 대응

---

### 6. Jobs / Scheduler
역할:
- collect, briefing, all 등의 작업 단위 실행
- cron / docker compose / systemd 등과 연결

핵심 관심사:
- 작업 간 순서 보장
- 실패 로그 추적
- 재실행 안정성

---

### 7. Deployment / Runtime
역할:
- 서버에서 자동 실행
- webhook 기반 배포
- 로그 기록 및 운영 관리

핵심 관심사:
- git pull / docker compose 실행 안정성
- 권한 문제
- 서버 재부팅 후 자동 기동

---

## 대표 실행 단위

- collect: 뉴스 수집만 수행
- briefing: 브리핑 생성만 수행
- all: 수집 + 후처리 + 브리핑 전체 수행

---

## 설계 원칙

1. 각 단계는 가능하면 독립적으로 실행 가능해야 한다.
2. 장애가 나면 어느 단계에서 실패했는지 바로 보여야 한다.
3. 브리핑 품질 문제는 수집/분류/중복제거/선정 로직으로 분해해서 본다.
4. 운영 이슈는 코드 문제와 배포/환경 문제를 분리해서 본다.
